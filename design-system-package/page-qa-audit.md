## 0. 总体判断

当前样板已经从“AI Demo / 组件拼贴”推进到了“真实业务样板”的阶段：六个产品都有业务定位、AI 边界、主任务、结果/记录区和基础交互。

但如果要给产品、设计、前端直接落地，还不能只看视觉是否好看。当前更关键的是交互选择是否稳定：

- 页面是否先声明产品模式，而不是直接堆组件。
- AI 输入是否在真正需要时前置，而不是所有页面都强行前置。
- 结果区、确认区、记录区是否有清晰父子关系。
- 抽屉、弹窗、行内展开、新页面是否有明确使用边界。
- 业务记录是否表达结果和下一步，而不是普通日志。
- 组件样式是否从组件库统一继承，而不是页面私有修补。

## 2. 共性问题与规范要求

### 2.1 模块间距

问题：

- 多个页面出现步骤条、摘要条、结果区贴在一起的情况。
- 视觉上看不出“一个模块内部的上下文”还是“两个独立模块”。

规范：

- 独立模块之间使用 `Layout/Space/ModuleGap = 24px`。
- 同一模块内部的相关分组使用 `Layout/Space/SectionGap = 16px`。
- 强从属关系可以使用 8-12px，但必须有清晰标题或背景层级。
- 如果两个容器贴在一起，就必须合并成一个容器，并建立 header / body / footer。

### 2.2 按钮尺寸与动作密度

问题：

- 有些页面主按钮、次按钮、上传按钮、记录按钮大小不统一。
- 文本按钮过多，导致页面像“按钮墙”。

规范：

- 主按钮：36-40px 高，承载业务提交或生成。
- 次按钮：与主按钮同高，但视觉权重降低。
- 工具动作使用 IconButton：上传、附件、语音、展开、删除、复制、下载。
- 记录行内动作最多暴露 1 个主动作 + 1 个展开/详情动作，其余进入更多或详情。

### 2.3 标签对齐与语义

问题：

- 局部标签文字偏上或状态标签像装饰。

规范：

- Tag 必须 `inline-flex` 垂直居中。
- Tag 只表达状态或来源，不用于“AI 感”装饰。
- 字段状态、员工状态、任务状态、来源状态不能混用同一套文案。

### 2.4 步骤条统一

问题：

- 服务单加急、智能特单、智能入职的步骤条样式和间距仍需完全一致。
- 曾出现步骤条下方双分割线。

规范：

- 所有任务处理页统一使用 `Component/Navigation/StepStrip`。
- StepStrip 只表达当前流程进度，不承载提示文案。
- StepStrip 与下方模块之间至少 16px；如果下方是独立卡片，使用 24px。
- 不允许双分割线。

### 2.5 输入区优先级

问题：

- 有的页面输入区被模式按钮、模板区或记录区挤弱。
- 有的页面在生成后仍让输入区占据过多位置。

规范：

- 输入前：输入区是主任务的页面，要放在首屏中心。
- 生成后：结果表、确认表单或政策答案变成主任务，输入区应收敛为“当前任务摘要 + 修改输入”。
- 运维后台和嵌入式流程不应把 AI 输入前置。

### 2.6 记录区可读性

问题：

- “查看 / 查看全部 / 查看全部 3 条”这类动作语义不清。
- 单条记录的信息散在左右，留白过大。

规范：

- 记录模块入口统一用“展开全部记录”或“查看完整记录”。
- 单条记录动作统一用“继续处理 / 查看详情 / 查看进度 / 导出结果”等业务动词。
- 记录行顺序：状态、业务标题、结果摘要、负责人/时间、下一步、展开。
- 最近记录默认展示 1-3 条；完整记录用展开区、抽屉或独立记录页。

## 3. 逐页审计

### 3.1 智能入职

交互模式：任务处理型。

正确方向：

- 输入客户资料是初始主任务，符合 AI 输入前置。
- 生成后以员工信息确认表为主，符合“结果表优先”。
- 有入职记录入口，记录不再作为首屏大块喧宾夺主。

必须保留：

- 客户/租户前置。
- AI 只生成草稿，确认后提交。
- 员工异常优先排序。
- 字段映射和员工确认表格支持横向滚动。

待修重点：

- 生成后当前任务摘要与步骤条、确认表格必须形成明确层级，避免看起来是两个容器贴合。
- 提交规则与提交结果需要放在同一个提交容器中，不能像结果区的附属卡片。
- 记录入口应只保留一种全量入口文案，例如“展开全部记录”。

建议：

- 默认态：输入卡 + 最近记录。
- 解析完成态：当前任务摘要 + 员工确认表 + 提交区；输入卡折叠。
- 员工详情：用 Drawer。
- 单字段补充：优先行内或 Drawer，不开新页。

### 3.2 智能特单办理

交互模式：意图分流型。

正确方向：

- 页面名称已从问答转向“办理 / 草稿生成”。
- 自然语言输入后生成 AI 识别结果和业务表单。
- AI 不自动提交，用户确认后提交服务单。

必须保留：

- 描述需求 → AI 识别 → 确认表单 → 提交服务单。
- 业务表单确认是主结果，不是普通回答。
- 缺失字段、需确认字段必须显性标记。

待修重点：

- AI 识别完成摘要和 AI 识别结果如果是同一阶段，应合并到一个容器；如果是两个阶段，必须有 24px 模块间距。
- 附件上传用 IconButton 或 Upload 图标模式，不应和主按钮同权重。
- 记录区 Tab 宽度要 hug content，“全部”不能被撑大。

建议：

- 初始态：一个主输入卡，场景标签作为辅助。
- 识别完成态：AI 识别摘要小条 + 表单确认主卡。
- 表单字段修改：当页直接改。
- 员工详情：Drawer。
- 提交确认：Modal。

### 3.3 AI 政策库 / 小鲲

交互模式：可信问答型。

正确方向：

- 政策问答保留对话/输入结构是合理的，因为问题本身是主任务。
- 输出应是政策方案，而不是普通聊天文本。
- 来源依据、推荐追问、导出和反馈都应保留。

必须保留：

- 可信度摘要。
- 结论摘要、政策要点、办理清单、风险提示、参考依据。
- 来源类型区分：原文政策、政策解读、案例、经办规则。
- 条目级反馈。

待修重点：

- 回答模式按钮不能横向挤压输入框，可改为输入区上方轻量 Segmented 或下方“模式”下拉。
- 发送按钮不应占用过宽横向空间，建议用固定宽度按钮或 IconButton。
- 常用任务模板不应是大面积按钮墙，应改为“重点模板 + 分组列表”。
- 首页态和回答态要分开：回答后主区域是答案和来源，不是模板。

建议：

- 首页态：输入区居中偏上，模板为辅助。
- 回答态：用户问题 + 结构化答案 + 来源面板 + 底部输入。
- 来源详情：Drawer。
- 订阅政策：Modal。
- 多城市对比：Drawer 或页面内配置面板；结果表全宽。

### 3.4 服务单加急

交互模式：流程嵌入型。

正确方向：

- 左侧服务单事实、右侧 AI 判断的两栏是合理的。
- AI 不承诺完成时间，只给判断和留痕建议。
- 权限不足时走审批申请，符合高风险动作边界。

必须保留：

- 服务单号、节点、停留时长、客户紧急原因。
- 规则判断、权限校验、不可承诺边界。
- 人工确认和留痕。

待修重点：

- 顶部提示条和步骤条要分成两个明确模块，不能贴在一起。
- StepStrip 必须与其他页面同款。
- AI 加急判断卡要突出“判断结果”和“下一步”，不应和服务单事实同权重。

建议：

- 两栏比例：左 65 / 右 35。
- 判断详情：右侧卡内展开。
- 高风险确认：Modal。
- 审批记录：表格或记录列表。

### 3.5 智能助手

交互模式：对话动作型。

正确方向：

- 对话区 + 动作面板是合理的。
- 用户问题可能需要多轮澄清，因此保留对话结构。
- 右侧动作面板应承接服务单草稿、政策答案、工具调用和人工接管。

必须保留：

- 聊天输入是连续 composer，而不是普通表单输入 + 按钮。
- 识别出的任务必须转为可执行动作。
- 发送客户回复前必须人工确认。

待修重点：

- 输入框和发送按钮应合并成对话输入条，发送用固定右侧按钮或图标按钮。
- 右侧动作面板要先展示最可执行动作，再展示工具调用、兜底路径。
- 最近处理记录不能抢主流程。

建议：

- 两栏比例：左 60 / 右 40。
- 对话消息：左/右气泡。
- 附件、语音、发送：IconButton。
- 动作详情：右侧面板或 Drawer。

### 3.6 智能咨询运营后台

交互模式：运营配置型。

正确方向：

- 运营后台不需要大 AI 输入框。
- Agent 依赖、配置详情、异常处理、失败样本回流是主任务。

必须保留：

- Agent 与依赖状态表。
- 配置详情。
- 待处理异常。
- 失败样本回流。
- 发布、回滚、修复、补字段等运营动作。

待修重点：

- 卡片容器与背景的对比度要提高，确保模块边界可见。
- 异常项内按钮和字段说明至少 8-12px 间距。
- 指标卡不能太淡，否则像背景上的文字。

建议：

- KPI 用低边框白卡 + 明确阴影或背景差。
- Agent 表为主，右侧详情为辅助。
- 失败样本用表格。
- 发布/回滚用 ConfirmBar + Modal 二次确认。

## 4. 面向角色的使用方式

### 产品经理

写需求前先回答：

- 这是六种页面模式中的哪一种？
- 用户首屏最重要的动作是什么？
- AI 输出到正式业务数据前，必须确认什么？
- 异常处理和记录追踪放在哪里？
- 详情是抽屉、弹窗、行内展开还是新页面？

### UI 设计师

画页面前先确认：

- 主任务是不是被最大视觉权重表达出来。
- 模块之间是否按 24 / 16 / 8 的关系拉开。
- 步骤条、Tag、Button、RecordList 是否来自源组件库。
- 两栏/三栏是否有任务依据，而不是平均分空间。
- 输入区是否应该前置，还是应该让结果区前置。

### 前端工程师

实现前先确认：

- 当前页面对应哪个 Template。
- 交互状态是否覆盖 default / loading / generated / editing / confirm / submitted / failed。
- Drawer、Modal、Popover、InlineExpansion 是否有独立状态。
- 表格、记录、字段状态是否使用 manifest 中定义的组件和 class。
- 是否能用 Code Connect 映射到 Figma 组件。
